Checkpoint قبل Task 5 — ليه الـ session بتحتاج proxy
المكان في الاستاك: Next.js App Router + @supabase/ssr + cookies
مرتبط بـ: Task 2 (اللوجين) و Task 5 (أول query على جدول leads)

==================================================
المشكلة
==================================================

لما بتعمل login، Supabase بيحط الجلسة في cookies. جوّا العلبة حاجتين مختلفتين:

- access token: ده اللي getClaims و RLS بيصدقوه. يعيش حوالي ساعة.
- refresh token: مفتاح تجيب بيه access token جديد من غير باسورد. يعيش أطول (أيام).

عمود Expires في DevTools (~2027) = امتى البراوزر يرمي العلبة.
expires_at جوّا قيمة الـ cookie = امتى الـ access token يبطل.

من غير proxy، بعد ما الـ access token يموت:
- السيرفر يقدر يجدّد في الميموري بتاع الريكوست الحالي (عشان كده الهوم ممكن تفتح وأنت فاكر إنك تمام).
- محدش بيحفظ التوكن الجديد في الـ cookie.
- البراوزر يفضل ماسك توكن ميت.

الصفحة تقدر تبان شغالة. اللي بيتكسر بعدين:
- RLS يرفض صفوف leads لأن الـ JWT الواصل لـ Supabase بايظ — قائمة فاضية أو error من غير فورم لوجين.
- أو فجأة getClaims فاضي وredirect لـ /login، خصوصًا لو Supabase بدّل الـ refresh token (rotation) والجديد اتريمي لأن محدش كتبه.

==================================================
ليه Next.js منعت الـ Server Component يكتب cookies
==================================================

Server Component (صفحة من غير "use client"، زي page.tsx) شغلها: اقرأ داتا وطلّع HTML.

أثناء الرسم، Next.js بيمنع التغييرات اللي بتفضل بعد الـ response — وSet-Cookie من النوع ده.

لو الصفحة وهي بترندر قدرت تحط cookie:
- الـ HTML ممكن يتخزّن في كاش ويتقدم لحد تاني → حد ياخد session حد تاني.
- الرسم ممكن يكون بدأ يتبعت للمتصفح قبل ما تعرف إنك محتاج تغيّر cookie.

فالقاعدة: القراية مسموحة. الكتابة وأنت بترندر لأ. cookies().set() في المكان ده بيرمي error.

عشان كده server.ts فيه setAll جوّه try/catch فاضي: مش حل، ده «متوقعّش الصفحة». الكتابة ناقصة لحد ما حد تاني يقدر يعملها.

==================================================
مين يقدر يكتب ومين لأ
==================================================

- LoginForm (براوزر): يقدر يكتب. عشان كده اللوجين اشتغل من غير proxy.
- page.tsx / getClaims (Server Component): يقرأ، ومش يكتب وهو بيرندر.
- proxy: بيشتغل قبل الصفحة، ويقدر يحط Set-Cookie على الـ response.

server.ts مش تابع لصفحة. ده ورشة تصنيع عميل Supabase للسيرفر: بيعلّم المكتبة إزاي تقرأ/تكتب cookies في Next.js. العجز من مكان الاستخدام (أثناء الرندر)، مش من الملف نفسه.

==================================================
حل الـ proxy — الفكرة مش الكود
==================================================

proxy.ts في Next.js 16 (زمان اسمه middleware) شغال قبل ما الصفحة تترندر. هو المكان اللي يقدر يعمل التلاتة مع بعض:

1. يجدّد التوكن (نداء getClaims هو الزرار اللي يخلّي التجديد يحصل).
2. يكتب التوكن الجديد على الـ request — عشان الـ Server Component اللي بعده يشوفه ومتحاولش تجدّد تاني.
3. يكتب على الـ response — عشان البراوزر يبدّل العلبة.

من غير 2: الصفحة تشوف توكن قديم.
من غير 3: البراوزر يفضل على الميت، وكل ريفريش نفس المشكلة.

matcher: فلتر. الـ proxy يتطبق على الصفحات، مش على صور Next ولا الملفات الستاتيك.

الحماية (redirect لو مش عامل login) مش شغل الـ proxy عندنا. دي في page.tsx من Task 2. الـ checkpoint تجديد + حفظ بس.

==================================================
إزاي تستخدمه (باختصار)
==================================================

ملف واحد: src/proxy.ts جنب src/app/.
Next.js بيدوّر على export اسمه proxy.

نفس createServerClient بتاع server.ts، بس مصدر الـ cookies هو الـ request/response مش cookies() بتاعت الصفحة.

بعد ما تبني العميل: نادي getClaims، وارجع نفس الـ response اللي اتكتب عليه. لو رجّعت response جديد من غير ما تنقل الـ cookies، التجديد ضاع.

==================================================
بدائل — امتى أنهي
==================================================

- من غير proxy: اللوجين والـ redirect في Task 2 يشتغلوا. أول مكان الـ cookie الميتة توجع هو Task 5 لما useLeads يضرب جدول leads. مش بديل؛ ده اللي كنا عايشين عليه قبل الملف.
- نعتمد على عميل البراوزر (client.ts) يجدّد ويكتب: البراوزر يقدر، فالقائمة ساعات تفضل شغالة من غير proxy. ده مش يغني عن الملف: الصفحات السيرفر وgetClaims لسه مش بيقدروا يحفظوا.
- نكرّر حارس الـ /login جوّا الـ proxy: زيادة. موجود في الصفحات. متكرّرش.

الرسمي: Server Components can't write cookies → لازم Proxy يجدّد ويخزّن.

==================================================
دليل شفناه في المشروع
==================================================

علبة الـ cookie مكتوب عليها 2027. جوّاها expires_at كان 25 أغسطس والهوم فتحَت في سبتمبر. التجديد حصل في الميموري، والعلبة متتحدثتش. ده المرض، مش «الصفحة وقفت».
